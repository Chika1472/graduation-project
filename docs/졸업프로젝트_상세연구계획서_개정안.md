### 연구를 한 문장으로 설명하면

공연 활동이 많은 시기에 주변 음식점과 카페의 매출 규모와 야간 매출 비중이 어떻게 달라지는지 분석하고, 데이터의 의미와 연결 조건을 이해하여 이 분석을 재현하는 AI 서비스를 만든다.

**연구의 중심은 공개데이터를 연결하는 분석 서비스의 구현과 평가이다.** 실증분석은 서비스가 실제로 해결할 문제이면서 별도의 연구 결과가 된다. 온톨로지 구축 자체나 대시보드 제작만으로 성과를 주장하지 않고, 같은 질문에 대한 분석 정확도와 근거 추적 가능성으로 평가한다.

| 단계 | 구체적인 산출물 |
| --- | --- |
| 데이터셋 구축 | 공연·공연장·상권·업종·분기별 매출을 연결한 패널 |
| 온톨로지 구축 | 기간·장소·업종·측정 단위·출처·허용되는 결합 규칙 |
| Agentic AI 구축 | 자연어 질문을 조회·집계·분석 도구 호출로 바꾸는 서비스 |
| 분석 및 평가 | 업종별 관련성 분석, 데이터 해석 오류와 답변 성공률 비교 |

**권장 범위:** 종로구·마포구의 분석 가능한 상권, 한식음식점과 커피·음료 업종, 2023-2025년 12개 분기, 도구 호출형 LLM 1종, 단일 에이전트, 웹 시제품 1개. 공간 경계의 호환성과 KOPIS 과거 자료를 먼저 확인하고 범위를 확정한다.

> 이번 개정에서는 서울시 매출 2022·2025년 파일과 점포 2025년 파일을 실제로 내려받아 구조와 결합 가능성을 점검했다. KOPIS 인증키를 이용한 수집, 상권 경계 원본 검증, 공연·매출 결합과 실증분석은 아직 수행하지 않았다. 문서의 예상 결과와 서비스 예시는 연구 설계이며 분석 결과가 아니다.

**읽는 순서:** 2-4장은 현실성과 연구 범위, 5-9장은 데이터와 변수, 10-11장은 서비스, 12-15장은 분석·확장·평가, 16-19장은 실행 계획과 출처다.

## 2 현실성 평가와 이번 수정의 이유

**판단: 범위를 제한하면 학부 졸업프로젝트로 타당하다. 다만 데이터 통합이 검증되기 전에는 완성 가능성을 확정할 수 없다.** 가장 큰 불확실성은 LLM 구현보다 공연 자료의 과거 제공 범위와 상권 공간 경계의 일치 여부다.

| 항목 | 현재 평가 | 계획에 반영한 결정 |
| --- | --- | --- |
| 서울시 매출·점포 확보 | 일부 연도 원본 확보·결합 확인 | 실증분석의 기반으로 채택 |
| 공연·공연장 확보 | 공식 API 명세 확인, 키 조회 미실행 | 첫 2주 안에 과거 표본 검증 |
| 공간 결합 | 경계 자료 게시 확인, 원본 미검증 | 코드·좌표계·경계 버전 확인을 선행 |
| 인과효과 추정 | 현재 자료만으로는 설득력 부족 | 고정효과를 이용한 관련성 분석 |
| 온톨로지·AI 구현 | 좁은 질의 범위라면 구현 가능 | 소규모 스키마와 고정 도구 사용 |
| 한 학기 일정 | 전국·전 업종·다중 에이전트는 과도 | 두 자치구·두 업종·단일 에이전트 |

### 기존안에서 바로잡은 부분

**시차를 핵심에서 보조로 옮긴다.** 분기 자료에서 다음 분기 계수를 추정할 수는 있지만, 공연 전후 며칠의 소비나 관람객 재방문을 설명하기는 어렵다. 대신 실제 파일에 있는 야간·주말 매출 비중을 추가해 해석 가능한 질문을 만든다.

**공연 작품 수와 활동량을 구분한다.** 등록된 공연이 10개여도 상연 횟수와 관객 규모는 다를 수 있다. 기본 지표와 개선 지표를 분리하고, 통계 API가 검증되면 상연 횟수를 우선 검토한다.

**‘온톨로지가 좋다’를 가정하지 않는다.** 일반 데이터 사전과 비교했을 때 오류를 줄이지 못하면 그 결과도 보고한다. 검증 규칙을 한쪽에만 넣어 비교가 불공정해지는 일을 막는다.

**호텔·컨벤션·신용위험 예측은 이번 범위에서 제외한다.** 여러 문제를 동시에 다루면 데이터 수집과 평가 기준이 분산된다. 교수님의 업종 간 관계 연구와 연결되는 공연·외식업 사례에 집중한다.

## 3 연구 배경·동기와 연구 질문

김태경 교수님이 참여한 음식점과 호텔 성과 연구는 서로 다른 업종의 공간적 관계를 탐색한다. 본 연구는 이 문제의식을 공연 활동과 외식업으로 확장한다. 음식점 품질이나 호텔 성과를 직접 재현하는 연구는 아니며, 공개자료로 수행 가능한 범위의 확장 사례다. [교수님 참여 논문 정보](https://khu.elsevierpure.com/en/publications/can-nearby-high-quality-restaurants-increase-other-tourism-firms-/)

공연 전후 식사와 음료 소비는 주변 매출과 연결될 수 있다. 그러나 혼잡에 따른 일반 방문객 감소, 공연장 내부 소비, 업종별 영업시간 차이 때문에 모든 업종에 같은 관계가 나타날 필요는 없다. 따라서 ‘공연이 많으면 매출이 오른다’는 결론보다 **어떤 매출 지표에서 어떤 차이가 나타나는가**에 초점을 둔다.

| 질문 | 검증 내용 | 우선순위 |
| --- | --- | --- |
| RQ1 매출 규모 | 같은 상권에서 공연 활동이 평소보다 많은 분기에 외식업 매출도 다른가? | 핵심 실증 질문 |
| RQ2 매출 구성 | 야간 21-24시 매출 비중이 달라지며 업종별 차이가 있는가? | 핵심 확장 질문 |
| RQ3 서비스 성능 | 온톨로지 활용이 단위·기간·공간 결합 오류를 줄이는가? | 핵심 시스템 질문 |
| RQ4 추가 탐색 | 주말 비중, 장르 차이, 1분기 시차에서 추가 패턴이 나타나는가? | 선택 분석 |

### 연구 동기와 가설

실제 비즈니스 데이터를 분석할 때의 어려움은 예측모형 선택만이 아니다. 데이터마다 시간 단위, 지리적 범위, 변수명이 다르고, 이를 잘못 연결하면 정교한 모형도 잘못된 답을 낸다. 본 연구는 이 문제를 온톨로지와 도구 실행 기록으로 다룬다.

H1은 공연 활동과 총매출이 양의 관련성을 보인다는 가설이다. H2는 야간 매출 비중과의 관계가 업종별로 다르다는 가설이다. 방향과 크기를 미리 단정하지 않고 양측 검정과 신뢰구간을 제시한다. 두 핵심 검정은 사전에 정하고, 나머지는 탐색 결과로 표시한다.

**이 연구의 차별점은 업종 간 현상 분석과 AI의 데이터 해석 능력 평가를 하나의 재현 가능한 사례로 연결한다는 데 있다.** 새로운 인과추론 기법이나 범용 에이전트 아키텍처를 발명하는 것을 목표로 삼지 않는다.

## 4 연구 범위와 착수 판단 기준

### 기본 범위

분석 단위는 **상권 × 업종 × 분기**다. 종로구와 마포구는 공연과 외식업의 결합을 살펴볼 후보 지역으로 제안한 것이며, 데이터 분포를 확인하기 전부터 충분한 표본이 있다고 가정하지 않는다. 표본을 유의한 결과가 나오는 곳으로 고르지 않고, 위치·자료 완전성·경계 호환성 기준으로 정한다.

대상 기간은 2023년 1분기부터 2025년 4분기까지다. 2023·2024년 매출·점포 파일의 게시 여부는 확인했으며 원본 검증은 후속 작업이다. 2022년은 회복기 특수성과 범위 확대 부담을 고려해 기본 분석에서 제외하고 필요할 때만 추가한다.

### 첫 2주의 단계별 확인

| 단계 | 통과 조건 | 미충족 시 조치 |
| --- | --- | --- |
| A 서울시 자료 | 목표 연도의 분기·업종 키, 필수 매출 항목과 점포 수 확인 | 공통으로 제공되는 기간으로 축소 |
| B KOPIS 표본 | 과거 1개월의 공연 목록·상세·공연장 ID와 위치 연결 | 오류 수정·제공기관 확인 후 재판단 |
| C 공간 결합 | 표본 5-10개 공연장의 위치와 주변 상권 연결을 지도에서 검수 | 경계 호환 자료를 확보할 때까지 본 분석 보류 |
| D 분석 가능성 | 상권별 여러 분기 관측과 공연 활동의 시간적 변동 확인 | 지역 확대 또는 사례 분석으로 조정 |

**중단 기준:** 2주 안에 과거 공연 자료와 호환 가능한 공간 경계를 모두 확보할 경로가 확인되지 않으면, 이 주제로 대규모 수집과 서비스 개발을 진행하지 않는다. 행정동 단위 자료로 전환하려면 결과변수와 공간 정의를 함께 바꾸고 지도교수와 범위를 다시 확정한다.

기본 구현은 2025년 한 분기, 공연장 5-10개로 끝까지 연결해 본 뒤 확장한다. 상권 내부·인접 공연장을 모두 포함하므로, 대상 자치구 바깥에 있어도 해당 상권에서 500m 이내인 공연장은 수집 대상이다.

**졸업프로젝트의 최소 완성 기준:** 결합 데이터셋, 문서화한 의미·검증 규칙, 재현 가능한 기본 분석, 작동하는 단일 에이전트, 비교 평가. 통계적 유의성이나 온톨로지의 우월성은 완성 기준으로 삼지 않는다.

### 실제로 필요한 접근 권한

이번 점검에서 서울시 매출·점포 파일은 API 인증키 없이 다운로드했다. KOPIS는 인증키 발급 후 실제 응답과 과거 기간의 제공 여부를 확인해야 한다. 공개 명세에 필드가 있다는 사실만으로 모든 기간·시설의 데이터가 반환된다고 확정하지 않는다.

### 파일을 받을 때 함께 남길 정보

원본 URL, 자료명, 조회 조건, 다운로드 일시, 파일 해시, 원본 파일명, 이용조건을 기록한다. 분석을 시작한 뒤 원본이 갱신되더라도 같은 결과를 재현할 수 있도록 수집본을 고정한다. 서울시 자료는 공식 출처와 이용조건을 결과물에 표시하고, KOPIS 원본 재배포 범위는 실제 이용조건을 확인해 정한다.

**공간 자료의 주의점:** 서울시 안내에는 공간 단위 변경이 명시되어 있다. 최신 매출 파일과 게시된 경계 ZIP이 자동으로 같은 버전이라고 가정하지 않는다. 지도에서 그럴듯하게 보이는 것만으로 검증을 끝내지 않는다.

## 6 실제 다운로드로 확인한 내용

## 7 공연 활동을 무엇으로 측정할 것인가

### 기본 지표와 개선 지표

**기본 지표는 분기와 공연 기간이 겹치는 등록 공연 ID 수**다. 한 공연을 월별 조회에서 여러 번 발견해도 같은 분기에서는 한 번만 센다. 이 값은 공연의 다양성과 등록 활동을 나타내며, 실제 상연 횟수나 관객 수를 직접 나타내지 않는다. 장기 공연의 휴연일도 식별하지 못할 수 있다.

**개선 후보는 상연 횟수다.** KOPIS 개발가이드의 ‘공연별 통계 목록’에는 공연 ID와 상연 횟수가 제시되어 있다. 시설별 통계에는 상연 횟수와 총 티켓판매수도 있다. 본문 17·18번 API를 표본 조회한 뒤 기간 기준·합산 가능성·키 연결을 검증한다. [공식 개발가이드](https://kopis.or.kr/upload/openApi/%EA%B3%B5%EC%97%B0%EC%98%88%EC%88%A0%ED%86%B5%ED%95%A9%EC%A0%84%EC%82%B0%EB%A7%9DOpenAPI%EA%B0%9C%EB%B0%9C%EA%B0%80%EC%9D%B4%EB%93%9C.pdf)

### 수집·검증 순서

1. 승인된 인증키로 과거 1개월을 조회하고, 공연 ID를 상세 정보·공연장 ID와 연결한다. 날짜 필터가 개막일인지 기간 중첩인지 확인하며, 분석 시작 전 개막해 계속된 공연도 누락되지 않도록 수집 범위를 정한다. 조회 제한은 API별 명세에 맞춘다.

2. 17번 통계 API의 `mt20id`와 `prfdtcnt`를 확인한다. 월별로 겹치지 않는 기간을 조회한 뒤 합계가 분기 활동량으로 해석 가능한지 점검한다. 서로 겹치는 기간의 횟수는 합산하지 않는다.

3. 시설별 통계는 시설명·공연장명으로 반환되는 항목의 ID 연결을 따로 검수한다. 동명 시설과 복합 공연장의 홀을 이름 유사도만으로 자동 통합하지 않는다.

4. 기본 공연 ID 수와 상연 횟수의 순위·분포를 비교한다. 지표 선택은 매출과의 유의성보다 결측률, 정의의 명확성, 연결 품질로 결정하고 분석 전에 고정한다.

### 해석에서 지켜야 할 구분

KOPIS는 공연일자 기준 공연통계와 예매일자 기준 예매통계를 구분한다. 개별 API가 어느 기준을 적용하는지 확인해 저장하며, 두 기준을 같은 분기 활동량으로 섞지 않는다. 판매 티켓 수는 고유 관객 수나 실제 입장 인원과 동일하지 않다. [KOPIS 통계 설명](https://kopis.or.kr/por/main/main.do)

등록되지 않은 공연과 수집 실패는 ‘공연 없음’과 다르다. 조회 성공 여부와 제공 범위를 기록한 뒤에만 관측 가능한 0을 만든다. 통계 API가 검증되지 않으면 기본 지표를 유지하고, 연구 명칭도 ‘등록 공연 활동’으로 한정한다.

## 8 패널 구축과 공간 결합

### 원본에서 분석 테이블까지

연도별 CSV → 공통 열 이름·타입 정리 → 상권·업종·분기 키 검사 → 공연·공연장 정리 → 공간 관계 계산 → 분기별 집계 → 매출·점포와 결합 → 결측 및 표본 제외 보고 순서로 처리한다. 원본을 덮어쓰지 않고 각 단계의 행 수를 기록한다.

업종은 한식음식점 `CS100001`, 커피·음료 `CS100010`으로 시작한다. 코드는 문자열로 보존하고 분기는 연도와 분기 번호를 갖는 정식 기간 객체로 변환한다. 매출과 점포 테이블은 일대일 키 결합을 강제해 중복으로 인한 매출 부풀림을 막는다.

### ‘주변’의 조작적 정의

기본 노출 범위는 **공연장 점과 상권 폴리곤 사이의 최단거리가 500m 이하인 관계**다. 상권 안에 있는 공연장은 거리가 0이다. 상권 경계선만 사용하면 넓은 상권 내부 공연장이 잘못 제외될 수 있으므로 폴리곤 전체를 사용한다.

좌표계 설명과 실제 파일을 확인한 뒤 미터 단위 투영 좌표계로 통일한다. 위·경도를 그대로 미터 거리처럼 계산하지 않는다. 모든 해당 공연장을 연결하고, 가장 가까운 공연장 하나만 찾는 방식으로 대체하지 않는다. 300m·800m는 민감도 분석에 사용한다.

한 공연장은 여러 상권에 노출될 수 있다. 이는 주변 노출의 정의이지만, 상권별 공연 수를 합쳐 서울 전체 공연 수라고 보고하면 중복 집계가 된다. 공간 관계 테이블에 거리와 기준을 저장한다.

### 경계 변경과 행정구역

상권 ID가 같아도 도형이 바뀌면 같은 공간의 시계열인지 확인해야 한다. 경계 버전, 적용 기간, 코드 대응표를 보관하고 대상 연도와 일치하지 않는 관측은 조정하거나 제외한다. 신뢰할 수 있는 변환 없이 과거 매출을 현재 폴리곤에 억지로 배분하지 않는다.

대상 자치구는 공식 속성·대응 정보를 우선 사용한다. 자치구 경계에 걸친 상권은 사전에 정한 기준으로 처리하고 별도 표시한다. 분석 표본, 제외 이유, 공간 결합 실패 목록을 함께 제출한다.

> 상권 전체의 매출을 이용하므로 ‘공연장으로부터 500m 안에 있는 음식점만의 매출’이 아니다. 500m는 공연 노출을 상권에 부여하는 규칙이다. 큰 상권에서 노출 오분류가 생길 수 있어 상권 크기별 민감도를 확인한다.

## 9 분석 변수와 해석

| 변수 | 정의 | 해석할 때 주의할 점 |
| --- | --- | --- |
| 총매출 Y | 업종·상권·분기의 추정매출 금액 | 실제 개별 점포 장부 매출이 아닌 추정 집계 |
| 공연 활동 E | 주변 등록 공연 ID 수, 또는 검증된 상연 횟수 | 두 지표를 섞지 않고 버전·단위를 명시 |
| 야간 비중 N | 100 × 21-24시 매출 / 총매출 | 계수 단위는 퍼센트포인트 |
| 주말 비중 W | 100 × 주말 매출 / 총매출 | 분기 내 주말·휴일 구성의 영향 가능 |
| 저녁 비중 D | 100 × 17-21시 매출 / 총매출 | 탐색용. 실제 공연 종료 시각과 동일하지 않음 |
| 점포 수 S | 같은 키의 전체 점포 수 | 총점포 정의와 프랜차이즈 포함 여부 확인 |
| 프랜차이즈 비율 F | 프랜차이즈 점포 수 / 전체 점포 수 | 선택적 이질성 분석, 점포별 매출 구분 불가 |

### 0과 결측의 처리

총매출이 0이거나 누락되면 비중을 0으로 만들지 않는다. 분모가 양수이고 분자 항목이 유효할 때만 비중을 계산한다. 이번에 점검한 두 연도의 목표 매출 행은 총매출이 양수였지만 모든 기간에도 그렇다고 가정하지 않는다. 금액 합계의 일치 여부도 수집 연도마다 다시 검사한다.

### 점포 수를 사용하는 두 가지 관점

기본 모형은 상권의 **총매출**을 분석한다. 점포 증가도 상권의 변화일 수 있으므로 현재 점포 수를 무조건 통제하지 않는다. 보조 모형에서 점포 수를 추가한 결과를 비교하되, 이를 더 정확한 인과효과라고 부르지 않는다.

‘총매출 / 전체 점포 수’는 선택적으로 제시할 수 있는 상권 수준 평균이다. 매출 추정 모집단과 점포 모집단이 일치하는지 확인해야 하며, 개별 점포의 실제 평균 매출이나 기존 점포의 매출 증가로 해석하지 않는다.

### 매출 구성에서 할 수 없는 것

주말 매출과 야간 매출은 각각 제공되지만, 이 둘을 교차한 **주말 야간 매출**은 해당 항목만으로 계산할 수 없다. 연령대별 매출이 있어도 공연 관람객의 연령이나 실제 방문 동선으로 바꿔 해석하지 않는다. AI에도 같은 제한을 적용한다.

## 10 온톨로지와 데이터 구조

온톨로지는 ‘무엇을 같은 개념으로 보고, 무엇을 연결해 계산할 수 있는지’를 명시하는 설계다. 모든 숫자를 그래프에 복제하지 않고, 큰 매출·공연 집계 테이블은 SQL·Parquet에 두며 그래프는 의미와 관계를 관리한다.

| 개체·관계 | 저장할 내용 |
| --- | --- |
| Performance → Venue | 공연 ID, 개최 시설, 공연 기간, 장르 |
| Venue → AreaVersion | 공연장 위치, 상권 경계 버전, 거리, 연결 기준 |
| 관측값 → 분기·업종·상권 버전 | 관측값의 시간·업종·공간 단위 |
| Metric | 총매출·야간 매출·상연 횟수 등의 정의, 단위, 합산 규칙 |
| Source·DatasetVersion | 원본 출처, 수집 시점, 해시, 제공 범위 |
| AnalysisRun | 질의, 자료 버전, 변수, 표본, 모형, 도구 실행 결과 |

### 구현할 규칙의 예

**단위 규칙:** 매출 금액은 원, 야간 비중은 %, 공연 ID 수는 건, 상연 횟수는 회로 구분한다. 금액과 비중을 같은 효과 크기로 비교하지 않는다.

**시간 규칙:** `당월_매출_금액`을 공통 개념 `quarterly_sales_krw`에 연결하고, 원래 이름도 보존한다. 공연일 기준과 예매일 기준을 별도 속성으로 둔다. 분기 합계를 일별 실측치처럼 분해하는 요청은 지원 불가로 판단한다.

**공간 규칙:** 관측값은 단순 상권 ID뿐 아니라 경계 버전에 연결한다. 거리 기준이 다른 분석은 별도의 실행으로 기록한다.

**관계 규칙:** 일반적인 주변 관계를 인과관계로 저장하지 않는다. ‘공연이 매출을 증가시킨다’는 관계를 온톨로지의 사실로 먼저 넣으면 결과를 미리 결정하는 오류가 생긴다.

### 최소 기술 범위

RDFLib 기반 RDF 그래프와 소수의 명시적 조회로 시작한다. 클래스는 위 표의 범위, 관계는 약 10-15개를 목표로 한다. SHACL 또는 동일 의미의 결정적 검증 함수로 필수 키·단위·기간을 검사한다. 복잡한 추론 엔진과 대규모 그래프 서버는 필수가 아니다. [RDF 개념](https://www.w3.org/TR/rdf11-concepts/), [SHACL](https://www.w3.org/TR/shacl/), [PROV-O](https://www.w3.org/TR/prov-o/)

## 11 Agentic AI 서비스의 실제 동작

단일 에이전트가 질문을 해석하고 필요한 도구를 순서대로 호출한다. LLM이 숫자를 직접 추정하거나 회귀계수를 작성하지 않도록, 표·계수·신뢰구간은 검증된 분석 함수의 결과에서 가져온다.

| 도구 | 입력 → 출력 |
| --- | --- |
| resolve_concepts | 사용자 표현 → 업종·지표·기간·공간 정의와 지원 여부 |
| build_panel | 지역·기간·업종·거리 → 분석 테이블, 결측·제외 보고 |
| summarize_panel | 패널 → 분포·추이·표본 수·활동량 변동 |
| run_analysis | 사전 허용된 모형·변수 → 계수·구간·진단 정보 |
| compare_specs | 거리·표본 조건 → 결과 비교표 |
| render_evidence | 실행 기록 → 그래프·출처·한계를 포함한 결과 카드 |

### 질문에서 답변까지의 예

사용자: “마포구 카페는 공연이 많은 분기에 야간 매출 비중도 높아지는지 보여 줘.”

에이전트는 카페를 커피·음료 업종으로, 야간을 21-24시로 해석했음을 표시한다. 기간이 없으면 기본 분석 기간을 알리고 적용한다. 500m 노출 기준으로 패널을 조회하고, 유효 표본과 활동량 변동을 확인한 뒤 허용된 모형을 실행한다.

결과 화면은 **자료 범위 → 관측 패턴 → 모형 결과 → 불확실성 → 출처와 실행 ID** 순서로 구성한다. “관련성이 관측됐다”와 “공연 때문에 증가했다”를 구분한다. 자료가 부족하면 숫자를 만들어 내지 않고 부족한 항목을 설명한다.

### 지원할 질문과 제한할 질문

지원: 업종별 총매출·야간 비중 추이, 공연 활동과의 관련성, 거리 기준별 결과 차이, 데이터 출처와 결측 현황.

지원 불가: 특정 공연 직후 3일의 매출, 주말 야간 교차 매출, 관람객 개인의 실제 소비, 개별 점포의 매출 증가. 제공 자료로 답할 수 없는 질문을 구분하는 능력도 평가한다.

최소 화면은 질문 입력, 분석 조건, 결과 그래프·표, 근거 카드 네 부분이다. 파일 업로드·로그인·결제·자동 영업 의사결정은 이번 구현 범위에 넣지 않는다. 도구 입력은 형식 검증을 거치고, 실행 가능한 모형과 변수 조합을 제한한다.

## 12 실증분석 방법

### 1단계: 표본과 분포를 먼저 이해하기

상권 수, 공연장 수, 업종별 분기 관측 수, 결측률, 0으로 관측된 공연 활동, 상권 내 활동량 변동을 제시한다. 지도와 시계열로 극단값·경계 문제를 확인하고, 전체 관측 수와 독립적인 상권 수를 구분한다. 공연 활동이 기간 내 변하지 않는 상권은 그 계수의 식별에 기여하지 못한다.

### 2단계: 고정효과 기본 모형

`log(Y_a,s,t) = α_a,s + λ_s,t + β_s log(1 + E_a,t) + ε_a,s,t`

a는 상권, s는 업종, t는 분기다. α는 상권·업종의 고정적인 차이, λ는 각 업종이 해당 분기에 공통으로 겪는 변화를 반영한다. 업종별 공연 활동 계수를 추정하고 차이를 검정한다. 양수 매출에 로그를 적용하며 누락을 0으로 바꾼 뒤 로그를 취하지 않는다.

이 모형은 “같은 상권·업종의 평소 수준과 같은 분기의 업종 공통 변화를 고려했을 때 공연 활동과 매출이 어떻게 함께 움직이는가”를 살펴본다. 시변 교란과 역인과가 남기 때문에 β를 인과효과로 단정하지 않는다.

### 3단계: 야간 비중 모형

결과변수를 0-100 범위의 야간 매출 비중으로 바꾸어 같은 구조의 모형을 적용한다. 계수는 퍼센트포인트 기준으로 보고한다. 선형 모형은 관측 범위에서의 평균적 관련성을 설명하는 용도로 사용하고, 범위를 벗어나는 예측과 잔차 패턴을 점검한다.

### 계수를 사람이 이해할 수 있는 비교로 바꾸기

공연 활동이 E0에서 E1로 달라질 때 로그 매출 모형의 비교값은 `100 × {exp[β × (log(1+E1)-log(1+E0))] - 1}`이다. 관측 범위 안의 비교를 사용하고 구간도 함께 변환한다. 이는 모형상 조건부 차이이며 정책 개입의 예상 수익이 아니다.

표준오차는 같은 상권의 반복 관측을 고려해 상권별로 군집화한다. 인접 상권의 공통 충격까지 자동 해결되는 것은 아니다. 상권 수가 작거나 활동량이 일부 공연장에 집중되면 유의확률보다 추정의 불안정성을 먼저 설명한다. [PanelOLS 문서](https://bashtage.github.io/linearmodels/panel/panel/linearmodels.panel.model.PanelOLS.html)

## 13 분석 전략과 결과의 신뢰성

기본 사양은 결과를 보기 전에 정한다. 주효과는 총매출과 야간 비중, 기본 노출은 500m, 기본 기간은 2023-2025년이다. 선택 분석이 많아질수록 우연히 유의한 결과가 나올 수 있으므로 핵심 검정과 탐색 검정을 분리해 보고한다.

| 확인할 문제 | 수행할 점검 | 해석 |
| --- | --- | --- |
| 주변 범위가 임의적인가? | 300m·500m·800m 결과 비교 | 방향·크기의 안정성 확인 |
| 일부 거대 공연장에 의존하는가? | 활동량 최상위 시설을 하나씩 제외 | 특정 사례 의존도 확인 |
| 결측 때문에 표본이 달라지는가? | 누락 특성 보고, 공통 관측 표본 비교 | 완전 사례 선택 편향의 가능성 확인 |
| 상권 크기가 결과를 좌우하는가? | 큰 상권 제외 또는 크기별 비교 | 공간 노출 오분류 민감도 확인 |
| 점포 수 변화와 연결되는가? | 점포 수 추가 사양과 기본 사양 비교 | 총매출 변화의 해석 보조 |
| 비중 증가가 금액 증가인가? | 야간 금액·총금액·비중 동시 확인 | 분모 감소에 따른 비중 상승 구분 |

### 시차 분석은 언제 추가할 것인가

현재 분기와 직전 분기의 공연 활동을 함께 넣는 사양은 선택적으로 수행한다. 12개 분기에서 시차를 넣으면 이용 가능한 기간이 줄고, 두 활동량의 상관이 높으면 계수가 불안정해진다. 자료 변동성과 표본 크기가 충분할 때만 수행하며 결과가 유의하다는 이유로 기본 사양을 대체하지 않는다.

### 필요한 만큼만 통제하기

같은 분기에 서울 전역에 공통인 변화는 분기 효과가 일부 흡수하지만, 지역별 관광수요·행사·교통 변화는 남을 수 있다. 유동인구나 점포 수는 공연 활동과 매출을 연결하는 경로일 수도 있다. 데이터를 많이 추가하는 것 자체를 인과적 설계의 개선으로 보지 않는다.

핵심 검정은 총매출 모형의 두 업종 계수가 모두 0이라는 공동 귀무가설과, 야간 비중 모형의 두 업종 계수가 같다는 귀무가설로 정한다. 이 두 검정의 Holm 보정 결과를 보조 보고하고, 업종별 계수·방향·신뢰구간을 함께 제시한다. 탐색한 사양을 공개하며 유의한 조합만 골라 제시하지 않는다.

**이 설계에서 DID를 바로 적용하지 않는다.** 공연 성수기에는 다른 수요도 함께 바뀔 수 있고, 지속적인 공연 활동은 명확한 단일 처치가 아니다. 추후 외생적인 공연장 휴관·개관 등과 비교 가능한 대조군이 확보되면 별도 연구로 검토한다.

## 14 추가하면 흥미로운 분석 네 가지

### 1. 총매출이 비슷해도 야간 매출 비중은 달라질까? · 우선 추가

공연 활동이 많은 분기에 총매출 변화가 작더라도 21-24시 매출 비중은 달라질 수 있다. 카페와 한식음식점의 방향이 다를 수도 있다. **총매출·야간 금액·야간 비중을 나란히 보여 주는 그림**을 만든다. 분기 집계로 실제 관람 전후 소비를 입증하지는 못하지만, 총매출만 보면 놓치는 매출 구성을 볼 수 있다.

### 2. 작품이 많은 곳과 상연이 많은 곳의 결과가 다를까? · 조건부 추천

서로 다른 공연이 많이 열리는 곳과 소수 장기 공연이 반복되는 곳은 ID 수가 비슷해도 활동량이 다르다. 통계 API가 검증되면 공연 ID 수와 상연 횟수의 순위를 비교하고, 각 지표를 사용한 결과 차이를 제시한다. 지표 선택이 결론을 바꾸는 사례는 온톨로지의 단위·집계 규칙이 왜 필요한지 보여 준다.

### 3. 아동 공연과 다른 공연은 업종별 패턴이 다를까? · 선택 확장

공연 메타데이터의 아동 공연 구분과 일반 공연을 한 번의 사전 정의된 분할로 비교한다. 카페·식사 소비와의 차이를 탐색할 수 있다. 표본이 작으면 회귀 상호작용을 늘리지 않고 기술통계에 그친다. 아동 공연이라는 분류만으로 실제 관객의 가족 구성이나 연령을 추정하지 않는다.

### 4. 프랜차이즈 비중이 높은 상권은 다른가? · 후순위

분석 시작 분기의 프랜차이즈 점포 비율로 상권 특성을 정하고, 공연 활동과 매출의 관련성이 다른지 탐색한다. 같은 분기의 비율을 사용할 때 생길 수 있는 동시 변화 문제를 줄이려는 선택이다. 다만 과거 비율의 존재가 외생성을 보장하지는 않는다.

점포 자료에는 일반·프랜차이즈 구분이 있지만 매출은 업종·상권 집계다. 따라서 **“프랜차이즈 점포가 독립 점포보다 더 이익을 얻는다”는 결론은 낼 수 없다.** 정확한 표현은 “프랜차이즈 비중이 다른 상권에서 패턴이 달랐다”이다.

**일정상 추천 조합:** 1번을 핵심 질문에 포함하고, 2번은 API 표본 검증이 성공하면 추가한다. 3·4번은 둘 중 하나만 선택한다. 주말 비중은 기존 변수로 만들 수 있어 기술통계에 포함하되, 여러 시간대·장르를 무제한 탐색하지 않는다.

## 15 온톨로지·AI 서비스 평가 설계

### 비교 실험의 공정성

**A: 데이터 사전 기반 에이전트. B: 온톨로지 기반 에이전트.** 같은 LLM 버전, 같은 데이터, 같은 의미 정보, 같은 분석 함수, 같은 검증 기능을 제공한다. A는 표·문서로, B는 그래프 관계 조회로 개념을 찾는다. 시스템 프롬프트는 검색 인터페이스 차이 외에는 가능한 한 동일하게 유지한다.

B에만 자료 정의나 검증 규칙을 추가하면 정보량 차이를 온톨로지 효과로 착각할 수 있다. 두 조건의 컨텍스트 예산과 도구 호출 상한을 같게 두고 실제 토큰·시간·오류를 기록한다. SHACL 검증의 효과를 따로 주장하려면 추가 실험이 필요하므로 기본 비교에서는 동등한 검증을 제공한다.

### 평가 질문 구성

개발용 10문항과 최종 평가용 30문항을 분리한다. 최종 문항은 단순 조회 6개, 다중 테이블 결합 8개, 회귀·사양 비교 8개, 답할 수 없는 요청 8개로 구성한다. 개발이 끝난 뒤 평가 문항과 정답 기준을 고정한다.

30문항 × 2조건 × 3회 실행으로 총 180개 응답을 평가한다. 정답 숫자는 독립적인 기준 SQL·분석 코드로 산출하고, 가능하면 일부 문항은 지도교수·동료의 검토를 받는다. 같은 목표를 달성하는 다른 유효 도구 순서를 오답으로 처리하지 않는다.

| 지표 | 판정 기준 |
| --- | --- |
| 과제 성공률 · 주지표 | 올바른 지표·기간·공간·표본을 사용하고 필요한 결과와 근거 제시 |
| 숫자 정확도 | 정수·건수는 일치. 회귀 원출력은 절대오차 0.000001 이내, 표시값은 지정 자릿수로 반올림한 기준값과 비교 |
| 오류 유형 | 월·분기 혼동, 중복 집계, 단위 혼동, 자료 없는 추론을 각각 집계 |
| 지원 불가 판단 | 불가능한 요청에 숫자를 만들지 않고 이유와 가능한 대안 설명 |
| 실행 비용 | 호출 수, 실제 지연시간, 토큰 사용량, 실패율 |

정확도는 자동 판정과 사전 체크리스트를 함께 사용한다. LLM의 자기 평가만으로 채점하지 않는다. 문항별 3회 결과를 묶어 비교하고 문항 단위로 불확실성을 추정한다. 반복 응답 180개를 서로 독립인 표본처럼 취급하지 않으며, 30문항 실험을 범용 AI 성능으로 일반화하지 않는다.

| 7-8주 | 도구 함수 연결, 단일 에이전트와 결과·근거 화면 | 28시간 |

| 11-12주 | 논문 작성·그림 정리·재현 확인·시연 준비 | 16시간 |

### 일정이 밀릴 때 줄이는 순서

선택 분석 → 시설별 티켓 지표 → 1분기 시차 → 고급 화면 기능 순서로 줄인다. 데이터 품질 검사, 기본 분석, 비교 평가, 출처 기록을 먼저 삭제하지 않는다. 온톨로지 실험이 주제의 핵심이므로 대시보드 꾸미기에 평가 시간을 빼앗기지 않도록 한다.

### 제안 기술 구성

Python·pandas로 정제하고 GeoPandas로 공간 관계를 계산한다. SQL 저장소는 DuckDB 또는 SQLite 하나를 선택한다. RDFLib로 의미 그래프를 관리하고 고정효과 회귀는 검증된 통계 라이브러리를 사용한다. 화면은 간단한 Python 웹 UI로 구현하며 별도 프런트엔드와 서버를 동시에 새로 만들지 않는다.

LLM은 도구 호출을 지원하는 한 모델로 시작하고 개발·최종 평가 시점의 버전을 기록한다. API 비용은 현재 요금과 파일럿 호출량으로 계산한다. 첫 10개 질문에서 사용량을 측정한 뒤 180회 평가 예산을 산정하고 호출 횟수·응답 길이에 상한을 둔다. 대규모 모델 학습과 GPU 구매는 필요하지 않다.

## 17 예상 결과·한계·완료 기준

### 어떤 결과가 나와도 연구가 되도록 설계하기

**긍정적 관련성:** 공연 활동과 총매출 또는 야간 비중이 함께 증가한다면, 어느 업종·지표에서 패턴이 나타나는지와 사양 변경에 얼마나 안정적인지 보고한다.

**혼합 또는 무관한 결과:** 총매출 관계는 작지만 매출 구성이 다르거나, 업종별 방향이 다를 수 있다. 효과가 관측되지 않으면 추정 구간과 측정 해상도·자료 범위의 한계를 설명한다. 유의하지 않다는 이유만으로 ‘영향이 전혀 없다’고 결론 내리지 않는다.

**시스템 개선이 없는 결과:** 온톨로지 조건이 일반 데이터 사전보다 낫지 않다면, 작은 스키마에서는 사전만으로 충분했는지, 검색·호출 비용이 늘었는지 분석한다. 이는 설계 선택의 근거가 되며 실패를 숨길 이유가 없다.

### 최종 산출물

| 산출물 | 완료로 판단할 조건 |
| --- | --- |
| 데이터셋과 사전 | 키·단위·결측·출처·버전과 표본 선정 과정이 재현 가능 |
| 온톨로지 | 실데이터의 핵심 개념·관계를 표현하고 잘못된 결합을 검사 |
| 분석 보고서 | 기본 사양과 민감도 결과, 추정 구간, 해석 범위를 포함 |
| AI 시제품 | 지원 질문에 도구로 답하고 근거·실행 기록을 보여 줌 |
| 평가 보고서 | 공정한 비교 조건, 문항·정답 기준, 성공률과 오류 유형 제시 |
| 졸업논문·시연 | 새로운 환경에서도 고정 데이터로 핵심 결과 재실행 가능 |

### 결과 서술의 기준

쓸 수 있는 문장: “자료와 모형 조건하에서 공연 활동과 야간 매출 비중 사이의 관련성이 관측되었다.”

쓸 수 없는 문장: “공연 개최가 음식점 매출을 증가시켰다”, “관객이 공연 후 이 음식점에서 소비했다”, “AI가 제안한 행사를 열면 매출이 오른다.” 이러한 주장을 하려면 별도의 식별 전략이나 더 세밀한 데이터가 필요하다.

서비스의 활용 대상은 학생 연구자와 상권 분석 담당자다. 결과를 의사결정의 참고 근거로 제공하되, 최적 매장 입지나 투자 수익을 자동 보장하는 서비스로 소개하지 않는다.

## 18 지도교수 상담용 설명과 첫 실행 목록

### 교수님께 설명할 때 사용할 문단

“교수님의 업종 간 관계 연구를 참고하여, 공연 활동과 주변 음식점·카페의 매출 규모 및 야간 매출 비중의 관계를 살펴보고 싶습니다. KOPIS 공연 자료와 서울시 상권 자료를 연결하되, 서로 다른 시간·공간·측정 단위를 온톨로지로 명시하려고 합니다. 이를 바탕으로 자연어 질문에 따라 데이터 조회와 분석 도구를 실행하는 서비스를 만들고, 일반 데이터 사전을 사용하는 경우보다 해석 오류를 줄이는지 평가하고자 합니다. 인과관계를 입증했다고 주장하기보다, 공개자료로 가능한 관련성 분석과 재현 가능한 서비스 구현에 범위를 두겠습니다.”

### 먼저 합의할 세 가지

**논문의 주된 기여:** 정보시스템·데이터 분석 서비스의 설계와 평가를 중심에 둘지, 실증분석을 중심에 둘지 확인한다. 본 개정안은 서비스 구현·평가를 중심에 두고 있다.

**범위:** 종로구·마포구와 두 업종으로 시작하며, 과거 공연 자료와 공간 경계가 검증된 뒤 표본을 확정한다. 결과가 흥미롭다는 이유만으로 중간에 지역·기간을 바꾸지 않는다.

**추가 분석:** 야간 비중은 포함하고, 상연 횟수는 자료 검증 후 반영한다. 장르와 프랜차이즈 분석은 일정에 따라 하나만 선택한다.

### 착수할 때 실제로 할 일

1. KOPIS 인증키 신청 경로와 이용조건을 확인하고, 승인 후 과거 1개월 표본을 수집한다.

2. 서울시 2023·2024년 매출·점포와 목표 기간의 공간 경계 자료를 받아 같은 품질 검사를 수행한다.

3. 상권 코드·경계 버전의 일치 여부와 표본 공연장 좌표 5-10개를 지도에서 확인한다.

4. 공연 → 공연장 → 주변 상권 → 업종별 매출의 연결을 한 분기에 대해 완성한다.

5. 이 결과를 보고 목표 기간·지역·기본 공연 지표를 확정한 뒤 본 수집과 개발에 들어간다.
