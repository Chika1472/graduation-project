## 외식업 10종 비교 결과

09번 기본 500m 모형은 **7,646행·134상권**을 사용합니다. 한 번만 관측된 상권×업종 15행을 제외했으며, 업종별 참여 상권은 40~126개로 다릅니다. 상권×업종 및 업종×분기 고정효과를 제거하고, 같은 상권의 여러 업종과 분기에 걸친 오차 상관을 군집 공분산에 반영합니다. 새 계산법은 기존 05번의 12개 대조에서 계수·표준오차·신뢰구간·p값을 최대 오차 8.15×10⁻¹³ 이내로 재현했습니다.

최종 재수집본을 반영한 전체 업종 동일기울기 검정의 p값은 총매출 **0.787**, 야간 비중 **0.189**이고, 두 검정의 Holm 보정값은 **0.787·0.378**입니다. 기본모형의 20개 업종별 기울기 검정도 BH FDR 0.05를 통과하지 못했습니다. **현재 자료에서 업종별 관계의 차이를 뚜렷하게 확인하지 못했으며, 관계가 없음을 입증한 것은 아닙니다.** 300/800m, 업종별 12분기 균형표본, 점포 수 통제를 함께 보고합니다. 업종별 균형표본은 모든 업종에 동일한 상권을 강제하는 표본이 아닙니다.

기존 두 업종 결과를 본 뒤 범위를 넓힌 **탐색 분석**입니다. 업종별 자료 제공 범위가 다르고, 인접 상권 간 공간 상관이나 공연 수 측정오차도 남아 있습니다. 공연 10개→20개 비교는 계산 예시로 제공하며 관측범위 표를 함께 제시합니다. 로그 매출의 역변환은 조건부 (매출+1)의 기하평균 상대차이로, 산술평균 매출 증가율이나 개입 효과가 아닙니다.

확장 데이터는 `data/analysis/food_industry_panel.csv`, 기본·민감도 결과는 `reports/09_industry_effects.csv`, 전체 업종 검정은 `reports/09_omnibus_tests.csv`에 있습니다. GEE 보조 결과와 FE 비교는 10번 노트북에서 확인합니다.

상세 수집 완료 반영 전후를 비교한 결과, 직전 948건 스냅샷과 **300·500·800m 공연 수가 모두 같고 18,120행 패널의 파일 해시도 같습니다.** 기본 500m 모형의 업종×결과변수 20개 계수·표준오차·p값도 동일합니다. 기존 시설명 연결을 공식 ID로 확인한 것이므로 통계 결론은 유지되며 연결 근거가 개선되었습니다. 변경표와 입력 해시는 `reports/08_snapshot_update_comparison.*`, `reports/09_snapshot_model_comparison.*`에 있습니다.

10번의 두 GEE 보조모형도 수렴·설계행렬·작업상관 검사를 통과했으며, FE와 사용한 7,646개 관측 키가 정확히 같습니다. GEE의 업종별 within 기울기 20개도 BH FDR 0.05를 통과하지 못했습니다. 표본이 같더라도 FE와 GEE의 평균구조·가중 및 추론 방식이 다르므로 결과의 차이를 모형 우열이나 인과 검증으로 해석하지 않습니다.

## KOPIS 상세 재수집 (2026-10-04)

[KOPIS_수집기.cmd](KOPIS_수집기.cmd)를 더블클릭해 제어 창을 열거나, [kopis.cmd](kopis.cmd)로 터미널에서 실행·중지·진행 상황 확인을 할 수 있습니다. 두 실행 파일은 프로젝트 최상위에 두며, 어느 작업 폴더에서 실행해도 파일 자신의 위치를 기준으로 프로젝트를 찾습니다. 수집 로직은 [07_KOPIS_상세정보_재수집.ipynb](notebooks/07_KOPIS_상세정보_재수집.ipynb)에 있으며 `.cmd`는 이 노트북의 실행용 셀을 불러오는 작은 진입점입니다. 기존 원본에서 미수집 ID를 계산하고, 시설 상세를 먼저 받은 뒤 연구지역 후보 공연 상세를 순차 요청합니다.

프로젝트 폴더에서 PowerShell 또는 명령 프롬프트를 열고 다음 명령을 사용하세요.

```powershell
.\kopis.cmd run             # 현재 창에서 실행·재개
.\kopis.cmd status          # 상태·남은 건수·진행률
.\kopis.cmd watch           # 다른 창에서 실시간 현황 보기
.\kopis.cmd stop            # 다른 창에서 중지 요청
.\kopis.cmd run --limit 1   # 미수집 ID 한 건만 확인
```

실행 창에서는 **Q 또는 Ctrl+C로 중지**할 수 있습니다. 진행 중인 HTTP 요청은 응답 또는 제한시간(30초)까지 기다린 뒤 저장·종료합니다. `watch` 창의 Ctrl+C는 현황 보기만 종료합니다. `run`을 다시 실행하면 정상 저장된 ID는 건너뛰며, 중복 수집 프로세스는 파일 잠금으로 막습니다. 수집은 현재 터미널에서 실행되므로 진행 중에는 그 창을 유지하세요.

호출 간격은 **1초**이며 동시 요청은 하지 않습니다. 실제 응답과 저장 시간이 추가되므로 이 프로세스는 초당 최대 1회 이하로 요청합니다. **HTTP 400은 같은 ID를 3초 뒤에 재시도**하며, 400이 계속되면 성공 또는 사용자 중지까지 반복합니다. 재시도 대기 중에도 Q·Ctrl+C·`stop`이 작동합니다. HTTP 401/403/429와 400 이외의 차단 응답은 중단합니다. 예상 남은 시간은 이번 실행에서 5건 이상 수집한 뒤 실제 속도로 계산하며 재시도 대기 중에는 재시도 상태를 표시합니다. 이전 실행 기록의 간격은 그대로 보존하고, 새로 연 수집기부터 변경 설정을 적용합니다.

- 최신 상태·확보 수·미수집 수: [latest.json](reports/kopis_collection/latest.json). 수집 중 매 건, 종료 시 최종 갱신합니다. `running`은 수집 중이며 완료를 뜻하지 않습니다. 실제 프로세스 실행 여부는 `status` 명령으로 확인합니다.
- 신규 원문: `data/raw/kopis_recollection/<회차>/`. 기존 `data/raw/kopis/`는 수정하지 않습니다.
- 통합 상세와 재개용 미수집 ID: `data/analysis/kopis_collection/`. 기존 `data/processed/kopis/`는 이전 수집 시점의 자료로 보존합니다.
- 통합 CSV는 25건마다 및 종료 시 갱신합니다. `worker.json`과 `worker.*.log`는 이전 백그라운드 실행의 이력이며 현재 CLI 상태는 `status`와 `latest.json`을 사용합니다.

기본 노트북 실행은 네트워크 없이 현황만 읽으며 `KOPIS_COLLECT` 환경변수로 자동 실행하지 않습니다. 실제 요청은 명시적인 CLI `run`/`start`에서 시작합니다. 인증키는 `KOPIS_API_KEY` 환경변수 또는 프로젝트 외부 `~/.config/grad/kopis.env`에서 읽고 화면·로그·공유 파일에 남기지 않습니다. 별도 `.py` 수집 소스나 추가 설치는 필요하지 않습니다.
